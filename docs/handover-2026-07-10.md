## Operational facts the next session needs (any machine)

- **Deploys**: the host runs a systemd timer, `spark-auto-upgrade.timer` (~15 min cadence), which downloads the latest GitHub release `.deb`. It is NOT an apt repo — `apt install spark` always reports "newest". To force a deploy: `sudo systemctl start spark-auto-upgrade.service`, then confirm `/healthz` reports the new version.
- **Release chain**: rebase-merge the fix PR → release-please opens `chore(main): release X.Y.Z` → merge it → the **tag-triggered** Release workflow builds and attaches assets. Watch that run specifically (the merge-commit run completes earlier and lies about readiness); the upgrade script now treats the asset-upload window as a clean retry (#61).
- **Pods vs podman**: `spark.service` runs as root and drives **root podman**. Any manual inspection or manipulation behind Spark's back needs `sudo podman`; user-level podman sees an empty store and silently succeeds at nothing.
- **Restarts are safe**: since v1.16.1, shutdown leaves pods running (`--drain-on-shutdown` to opt back in), the unit uses `KillMode=process`, and recovery re-adopts survivors with scheduler quota intact. Upgrades no longer touch workloads.
- **Verification norms**: a fix is done only after live acceptance on the node. `docs/devlog.md` entries carry the exact acceptance recipes used (e.g. two 60Gi pods for admission, exit-7 pod for status verdicts, crashy+healthy pair for per-container restarts).
